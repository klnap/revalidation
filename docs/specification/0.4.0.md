# `@klnap/revalidation` 0.4.0 specification

## Status

Approved design baseline for 0.4.0. Implementation and verification must follow this document.
Update it when repository or runtime evidence changes a decision.

## Goal

Provide a framework-independent event and cache-invalidation core with focused adapters for
Payload CMS, HTTP, and Next.js. Keep the ordinary Payload-to-Next.js path short while allowing
custom producers, consumers, transports, schemas, and cache operations.

Breaking changes from `0.3.0` are allowed. Do not add compatibility aliases for removed APIs.

## Scope and non-goals

- Use CloudEvents 1.0 structured JSON events and JSON batches.
- Sign default HTTP deliveries with Standard Webhooks.
- Accept Standard Schema V1 validators for application event data.
- Use generated CloudEvent IDs prefixed with `rev_`.
- Keep HTTP delivery direct and bounded. Do not add a persistent queue, broker adapters, an
  indexer, or a workflow engine.
- Keep Payload, transport, core, and cache-consumer code in separate package layers.
- Keep cache `tags` and `paths` in `defineRevalidation()`. They are not delivery destinations.
- Use `dispatcher.targets` only for named delivery destinations. Destination filters and explicit
  dispatch selection must not depend on consumer invalidation rules.
- Do not use a process-global registry.
- Do not claim that a Payload hook runs after commit unless an integration proves that callback
  ordering.

## CloudEvents profile

The package emits and accepts CloudEvents `1.0` in structured JSON form. A single event uses
`application/cloudevents+json`; a batch is a JSON array using
`application/cloudevents-batch+json`.
The receiver normalizes the media type case-insensitively and permits valid media-type parameters.
The media type and top-level JSON shape must agree: one object for the event format, an array for the
batch format.

Every event has non-empty `id`, `source`, and `type`, plus `specversion: "1.0"`. The package emits
an RFC 3339 `time`, `datacontenttype: "application/json"`, and JSON `data`; it does not emit
`data_base64`. The receiver requires a `data` member, accepts JSON `null` when its schema allows it,
accepts unknown valid extension attributes, and ignores them. It rejects unsupported specversions,
malformed required attributes, non-JSON payloads, and malformed batch members. Empty batches are
valid and perform no invalidation.

CloudEvent IDs use `rev_` followed by a cryptographically random UUID. A retry reuses the same
CloudEvent, including its ID. A producer source is an absolute URI; the Payload default is
`urn:klnap:revalidation:payload`. Deployments may configure another source URI.

The package's application event type is
`com.klnap.revalidation.resource.changed.v1`. Its `data` separates the triggering operation and
resource from the resources affected:

```ts
type Operation = 'create' | 'update' | 'delete'

type Resource = {
  type: string
  name?: string
  id?: string
  locale?: string
  slug?: string
  identifiers?: Record<string, string>
}

type RevalidationData = {
  operation: Operation
  resource: Resource
  affected: readonly {
    operation: Operation
    resource: Resource
  }[]
}
```

For Payload, collection resources use `type: "payload.collection"` and global resources use
`type: "payload.global"`. `name` is the collection or global slug. The `affected` list includes the
triggering resource and every known dependent resource. A dependent document is an `update` even
when the triggering media operation is a `delete`. Previous and current identifier values remain
separate affected entries so both cache identities can be invalidated.

CloudEvents `source + id` identifies an event. Standard Webhooks `webhook-id` identifies one HTTP
delivery. They are separate identifiers and serve separate purposes.

## Application schemas

Application data schemas use Standard Schema V1. Register them by CloudEvents source URI. Validate
each CloudEvent's `data` after verifying the HTTP
signature and validating the CloudEvents envelope. Await `validate()` for both synchronous and
asynchronous schemas, and pass its returned `value` to rules. Never use the original unvalidated
input when validation transformed it.

The built-in Payload schema validates the package's `RevalidationData` profile. Custom producers
may register schemas for their CloudEvent source. Envelope validation is package-owned and is not
delegated to application schemas.

Use `@standard-schema/spec` `1.1.0` for the public schema type. Use `standardwebhooks` `1.3.0` for
the signing and verification implementation. Do not add the CloudEvents SDK: the supported profile
is structured JSON and batches, and the SDK declares Node support only through 24 while this
package also supports Node 26.

## Public configuration shape

`defineRevalidation()` owns cache declarations, source schemas, rules, and the Next.js handler.
`tags` and `paths` remain separate properties:

```ts
import { defineRevalidation } from '@klnap/revalidation/consumers/next'
import { http } from '@klnap/revalidation/dispatchers/http'
import { revalidation } from '@klnap/revalidation/producers/payload'

// payload.config.ts
export default buildConfig({
  plugins: [
    revalidation({
      dispatcher: http({
        targets: {
          website: {
            url: process.env.REVALIDATION_URL!,
            secret: process.env.REVALIDATION_SECRET!,
          },
        },
      }),
    }),
  ],
})
```

The Next.js consumer declares the cache templates and event rules:

```ts
import { defineRevalidation } from '@klnap/revalidation/consumers/next'
import { payloadSchema, payloadSource } from '@klnap/revalidation/sources/payload'

const { tags, paths, POST } = defineRevalidation({
  secret: process.env.REVALIDATION_SECRET!,
  tags: { page: '[locale]:page:[slug]' },
  paths: { page: '/[locale]/[slug]' },
  sources: { [payloadSource]: payloadSchema },
  rules: ({ tags, paths }) => ({
    'payload.collection': {
      pages: ({ affected }) => ({
        tags: affected.flatMap(({ resource }) =>
          resource.locale && resource.slug
            ? [tags.page({ locale: resource.locale, slug: resource.slug })]
            : [],
        ),
        paths: affected.flatMap(({ resource }) =>
          resource.locale && resource.slug
            ? [paths.page({ locale: resource.locale, slug: resource.slug })]
            : [],
        ),
      }),
    },
  }),
})
```

Re-export the handler from the App Router:

```ts
// app/api/revalidate/route.ts
export { POST } from '@/revalidation'
```

Source registry keys are CloudEvents source URIs. The Standard Schema output type for each literal
URI flows into the `on()` callback selected by that URI. Object-mapped rule callbacks receive the
registered source-data union; use `on()` when a rule needs one source narrowed precisely.

Nested object mappings use resource `type` as the outer key and resource `name` as the inner key.
They match affected resources. An `on()` rule expresses selectors that need source, event type,
operation, root resource, or more specific affected-resource conditions:

```ts
import { defineRevalidation } from '@klnap/revalidation/consumers/next'
import { payloadSchema, payloadSource } from '@klnap/revalidation/sources/payload'

const { tags, POST } = defineRevalidation({
  secret: process.env.REVALIDATION_SECRET!,
  tags: { settings: 'settings' },
  sources: { [payloadSource]: payloadSchema },
  rules: ({ tags, on }) => [
    on(
      {
        source: payloadSource,
        operation: 'update',
        resource: { type: 'payload.global', name: 'settings' },
      },
      () => ({ tags: [tags.settings()] }),
    ),
  ],
})
```

Object mappings and `on()` rules produce the same rule representation and run through one matcher,
resolver, and deduplication path. A `rules` callback may return one object mapping, an array of
`on()` rules, or an array containing both mapping objects and `on()` rules. Source selectors use
the CloudEvents source URI, not a local alias.

## Selectors and cache invalidation

`defineRevalidation()` remains the single cache-consumer configuration factory. It continues to
declare `tags` and `paths` independently and returns their typed helpers with the configured
consumer handler. No second tag/path declaration factory is added.

Consumer rules match CloudEvent `source`, `type`, root `operation`, root `resource`, and/or
`affected` resources. Resource selectors match `type` and may narrow by `name`, `id`, or `locale`.
An affected selector matches when any affected entry satisfies it. If several entries match, the
rule receives all matching entries in event order.

Both object-mapped rules and `on(selector, resolver)` rules compile to the same internal rule
representation. Evaluate every matching rule; one rule does not shadow another. Collect all
resulting tag and path invalidations, then deduplicate identical operations by operation type,
value, and Next.js profile/path type. Preserve distinct profiles or path types.

Do not create a second cache-target grouping API. Existing `tags` and `paths` remain the named,
typed cache helpers.

The top-level `mode` defaults to `expire`; a rule-level `mode` overrides it. A tag result may be a
string or `{ value, mode }`, where `mode` is `expire`, `stale`, or a native Next.js `revalidateTag`
profile (`string | { expire?: number }`). A per-tag `mode` overrides its rule and top-level modes.
Map `expire` to `{ expire: 0 }` and `stale` to `"max"`. A path result may be a string or
`{ value, type }`, where `type` is `page` or `layout`. Plain tag strings use the selected default
mode. Plain literal paths omit the type; a path containing dynamic segments defaults to `page`.
Deduplication includes the resolved tag profile or path type.

The Next.js adapter uses framework-native `revalidateTag` and `revalidatePath`. Route Handler
execution uses `revalidateTag(tag, profile)`; it does not use `updateTag`, which is restricted to
Server Actions. Preserve the current default `expire` mode (`{ expire: 0 }`) and the `stale` mode
(`'max'`). Paths use `revalidatePath(path, pathType)` and do not take a cache mode. Omit
`pathType` for literal paths; dynamic route patterns require `page` or `layout`, defaulting to
`page`. Reject tags over 256 characters and paths over 1024 characters. Keep Next-specific imports
out of the core and Payload producer.

Keep advanced cache execution on the same `defineRevalidation()` factory. Named cache layers reuse
the same source schemas, selectors, rule compiler, and deduplication. The built-in `next` layer
executes tags and paths; custom layers provide an `execute` callback. A resolver may return ordered
`operations: [{ layer, value }]`; the callback receives the validated event context, `value`, and an
`AbortSignal`. Execute custom operations in order before Next.js invalidations. On failure, stop that
rule's remaining operations and skip its tag/path invalidations; continue independent rules. Return
HTTP 500 with per-operation results when any operation fails. Limit custom operations to 1,000 by
default and 10,000 maximum. Use a 15-second default execution deadline and a 60-second maximum.
The deadline ends the handler's wait and requests cooperative cancellation through `AbortSignal`;
it cannot terminate arbitrary JavaScript or reverse completed external side effects. A timed-out
operation remains failed even if it settles late; dependent operations and invalidations stay
skipped. Executors must honor the signal. This synchronous best-effort execution is not durable work.
Do not call cache layers `targets`; that name belongs only to delivery destinations.

## Delivery destinations and routing

The HTTP dispatcher accepts a named `targets` record:

```ts
http({
  targets: {
    website: { url: 'https://example.test/api/revalidate', secret: 'whsec_...' },
    storefront: {
      url: 'https://shop.example.test/api/revalidate',
      secret: 'whsec_...',
      filter: { affected: { type: 'payload.collection', name: 'products' } },
    },
  },
})
```

With no filter, a destination is eligible for every event. A configured filter selects events using
the same event-selector semantics as consumer rules. An event passes when it matches the target's
filter. An explicit `targets` list on a manual dispatch narrows the configured targets and never
bypasses their filters. Payload integration does not require target selection and fans out to all
eligible destinations.

Selectors support `source`, CloudEvents `type`, root `operation`, root `resource`, and `affected`.
String fields accept one exact value or a readonly list of exact values. A resource selector matches
its provided `type`, `name`, `id`, and `locale` fields; omitted fields are unconstrained. Multiple
fields in one selector are combined with AND. Affected selectors match when any affected entry
matches. No glob syntax or user-supplied predicate is required in the default API.

Each destination secret uses the `whsec_`-prefixed Base64 format. For each destination, filter the
input event list first, then split matching events into ordered chunks of at most `maxEventItems`
(default 100, hard maximum 1000). Send one event as a structured JSON event and multiple events as
a CloudEvents JSON batch. Each chunk is an independent signed delivery. An empty filtered list
performs no request.

Sign each destination's exact serialized request bytes with that destination's Standard Webhooks
secret. Verify signatures from raw request bytes before JSON parsing, with the SDK's five-minute
timestamp tolerance. Retries for one destination chunk reuse the exact request bytes and
`webhook-id`, but generate a fresh timestamp and signature for each attempt to keep timestamp
freshness meaningful. Each chunk and destination gets a distinct delivery ID.
Concurrency is bounded to four in-flight HTTP requests across the dispatch call.

Destinations are independent. A rejected or failed destination does not stop other destinations.
Keep an outcome for every destination chunk. Each outcome has `target`, `deliveryId`, `status`,
`attempts`, and an optional sanitized error. Status is `accepted`, `rejected`, `failed`, or
`unknown`; a chunk timeout is `unknown` because the receiver may have processed it.

The aggregate result is:

```ts
type TargetDispatchResult = {
  target: string
  deliveryId: string
  status: 'accepted' | 'rejected' | 'failed' | 'unknown'
  attempts: number
  error?: { code: string; message: string }
}

type DispatchOutcome =
  | { status: 'accepted'; results: readonly TargetDispatchResult[] }
  | { status: 'partial'; results: readonly TargetDispatchResult[] }
  | {
      status: 'rejected' | 'failed' | 'unknown'
      results: readonly TargetDispatchResult[]
    }
```

With zero delivery chunks, return `accepted` and an empty `results` array. If every chunk accepts,
return `accepted`. If at least one accepts and another does not, return `partial`. If none accepts,
return `unknown` if any chunk is unknown, `rejected` only if every chunk is rejected, and `failed`
otherwise. A receiver's `accepted` response means it accepted the request, not that every
configured cache operation succeeded.

An empty eligible destination set is a successful no-op. An explicit unknown destination is a
rejected dispatch and makes no network request.

Keep HTTPS as the default. Preserve only explicitly justified development and loopback exceptions;
`allowInsecure` must remain a clearly documented opt-in because it exposes the signing secret in
transit. Do not follow redirects.

Validate destination URLs at configuration time. Permit only `https:` by default; reject embedded
username/password and unsupported protocols. Log destination names and sanitized errors only, never
secrets, signatures, or request bodies.

## Payload producer behavior

Preserve collection/global opt-ins, operation hooks, identifiers and previous identifiers,
field exclusions, locale handling, publish and draft rules, orderable integration, media dependency
discovery, logging, and fail-open save behavior.

Represent one triggering Payload change as one CloudEvent with root `operation` and `resource`.
Add the root resource, prior/current identifier variants, orderable neighbors, and discovered media
dependents to `affected`. Keep each dependent resource's effective operation explicit.

Payload `afterChange` and `afterDelete` run before Payload commits. A delay is not a post-commit
callback. The ordinary plugin remains best-effort and fail-open; log construction and delivery
failures without rejecting the save. Preserve the deferral mechanism used by the
`revalidationOrderableHooks()` adapter: flush when the host calls `onCommitted` and discard when it
calls `onRolledBack`. This package tests its callback behavior, not the host's transaction ordering.
Do not claim post-commit behavior without an integration test against the host version in use. Do
not expose a generic caller-owned transaction API or add database-specific outbox tables without
an explicit requirement. Do not claim durable delivery.

## Reliability and outcomes

- HTTP attempts, retries, request body size, event count, concurrency, and total deadline remain
  bounded.
- Retry network failures, timeouts, `429`, and `5xx` within the overall deadline. Do not retry
  permanent `4xx` responses or redirects.
- Map a final `2xx` to `accepted`, a final permanent `4xx` to `rejected`, a final `5xx` or
  non-followed redirect to `failed`, and a timeout/network result without an HTTP response to
  `unknown`. A final `429` is `rejected`.
- Keep two retries by default, a 200 ms initial full-jitter bound, a 15-second per-attempt timeout,
  and a five-second total dispatch deadline. The deadline wins when it is shorter.
- The sender defaults to 100 events per destination chunk and caps the value at 1000. The receiver
  defaults to a 256 KiB streamed body limit and 100 events per request; hard ceilings are 16 MiB
  and 1000 events. Sender and receiver limits must agree.
- Keep a stable CloudEvent ID across retries. Keep a stable Standard Webhooks delivery ID across
  retries of one destination delivery.
- Duplicate delivery is possible after a timeout. Built-in cache invalidation must remain
  idempotent. Custom consumers should deduplicate by `webhook-id` when duplicate side effects matter.
- Keep per-target outcome detail. Do not equate successful HTTP acceptance with successful cache
  execution.
- A Next.js handler returns a server error when a matched cache operation fails. It may continue
  independent operations, but must report partial execution rather than claiming full success.
- The Next.js handler accepts only `POST` with the CloudEvents JSON event or batch content type.
  Return `405` for other methods, `415` for unsupported content types, `413` for body/event limits,
  `401` for invalid Standard Webhooks authentication or timestamp, and `400` for malformed JSON,
  envelopes, sources, or schema data.
- Validate every event in a batch before executing any cache operation. Invalid input rejects the
  whole request without partial side effects.
- Execute independent cache operations even if one operation throws. Return `500` if any operation
  fails, with structured partial results; otherwise return `200`. A retried request may repeat the
  successful operations, so invalidations must remain idempotent.

## Public API and removed surface

- Keep one `defineRevalidation()` factory.
- Keep `tags` and `paths` as the cache-definition properties.
- Add rules based on the new CloudEvents/resource profile, including object mappings and `on()`.
- Keep `dispatcher.targets` distinct from consumer rules.
- Keep the core `Dispatcher` and event/rule contracts framework-independent. Custom producers may
  inject a dispatcher; custom consumers may reuse event validation and rule resolution, then execute
  operations with their own cache adapter. Do not make Payload or Next.js runtime imports mandatory
  in the core.
- Remove `defineRevalidationTags()` and its `/consumers/next/tags` export. Do not add aliases.
- Remove the old ad hoc `source`/`data` envelope and bearer-token HTTP protocol.
- Keep public exports explicit and verify them from the packed tarball.

## Verification gates

Before release consideration, prove:

1. CloudEvents single and batch JSON profile interoperability, including invalid envelope cases.
2. Standard Webhooks signing and verification against official vectors; raw-body, timestamp,
   multi-signature, malformed-header, and replay-window behavior.
3. Standard Schema V1 sync, async, failure, and transformed-output behavior.
4. Named destination filtering, explicit-selection intersection, bounded fan-out, independent
   retries, and partial outcomes.
5. Payload locale, publish, identifier, exclusions, orderable, and media-dependency behavior.
6. Payload's pre-commit limitation and explicit deferral behavior without claiming a generic
   post-commit hook.
7. Real Next.js production behavior for tag profiles, paths, Route Handler verification, and
   partial failures.
8. Packed-package Node consumers, declarations, exports, and documented quick starts.

No package publication, version tag, GitHub Release, commit, or push is part of this task.
